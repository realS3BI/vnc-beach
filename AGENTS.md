## Project Instructions

- Goal: a VNC server and viewer that work on macOS and Windows and stay free. Interoperability with standard VNC clients/servers (RFB 3.8, RFC 6143) is a hard requirement; don't add proprietary protocol changes without a negotiated (pseudo-)encoding or security type.
- The product is called "VNC Beach" in everything a user sees (UI, window title, tray, README, website); crate, binary, file and path names stay `vnc-beach`/`beach-*`.
- README and user-facing UI text are German with real umlauts (`Zurück`, not `Zurueck`). Code, comments, log messages and CLI help are English.
- Protocol logic belongs in `crates/rfb` with unit tests; platform code (capture, input, clipboard) stays in `beach-server`; UI in `beach-viewer`.
- Run `cargo test --workspace` and `cargo build --workspace` before finishing. Windows code can't be compiled on the Mac (Homebrew Rust, no Windows target). Sebastian's PC (SSH host alias `sebastian-pc` from `~/.ssh/config`; address and key are not in this repo) has a GNU toolchain: sync the source to `%LOCALAPPDATA%\vnc-beach\src` (tar over SSH with `COPYFILE_DISABLE=1`) and build with `%LOCALAPPDATA%\vnc-beach\cargo.cmd build --release --workspace`. Note that `xcap::Monitor` is not `Send` on Windows.
- The installed viewer on the PC is `%LOCALAPPDATA%\Programs\vnc-beach\vnc-beach.exe` (Start menu: `VNC Beach`). Copy a new build there after changes; the running viewer and the `--background` tray process must be stopped first (`Get-Process vnc-beach | Stop-Process`). SSH sessions can't show a tray icon: start `vnc-beach.exe --background` through a one-off `schtasks /it` task so it runs in the user's desktop session.
- Windows service (`beach-viewer/src/service.rs`, service name `vnc-beach`): `--install-service`/`--uninstall-service` run elevated (the SSH session on the PC is already elevated), copy the exe to `C:\Program Files\VNC Beach` and add the firewall rule "VNC Beach (Dienst)". The service starts `--service-agent` as SYSTEM in the console session; it runs `background::run_agent` and answers the control channel on `service.port`, and the tray process forwards to it (`State::delegated`). Capture/input threads follow the input desktop (`beach-server/src/desktop.rs`), which is how the lock screen works. Logs: `C:\ProgramData\VNC Beach\{service,agent,setup}.log`. After a new build, rerun `vnc-beach.exe --install-service --config-dir %APPDATA%\vnc-beach --home %USERPROFILE%` so the service copy is updated. The PC has it installed, Tailscale in unattended mode and Fast Startup off. The tray process runs `service::ensure()` at start (the viewer starts the tray if none runs): it installs or updates the service when it is missing, older than the running exe (`--version` of the Program Files copy) or Tailscale isn't unattended, and remembers a declined UAC prompt per version in `config.toml` (`service_declined`). On macOS the same `ensure` writes the login window LaunchAgent `/Library/LaunchAgents/at.schlossers.vnc-beach.loginwindow.plist` through an `osascript` admin prompt (only for an installed, non-translocated `.app`); Tailscale's switch to `tailscaled` is `crates/beach-viewer/src/tailscale-daemon.sh`, opened in Terminal from the settings. The macOS login window/lock screen path is untested: never log out, lock or restart Sebastian's Mac (or the Mac mini) to try it without asking, and don't run the viewer on this Mac casually, since it now starts the tray, enables autostart and asks for the admin prompt.
- Headless Windows (`beach-server/src/headless.rs`, docs in `docs/headless-windows.md`): while no monitor is active, the capture thread adds one 2560×1440 display through the Amyuni `usbmmidd_v2` driver and removes it when a monitor returns; ownership is the marker `C:\ProgramData\VNC Beach\virtual-display`, and displays the driver can't attribute are never touched. The driver is installed by `vnc-beach.exe --install-display-driver` (elevated, `beach-viewer/src/display_driver.rs`, pinned SHA-256 of the vendor zip). The `real_virtual_monitor_cycle` test changes the PC's real display arrangement: run it only when asked.
- To see the tray process's log on the PC, start it through `cmd /c set RUST_LOG=debug&& vnc-beach.exe --background > %TEMP%\vnc-beach-bg.log 2>&1` (via the `schtasks /it` trick); the viewer logs clipboard and server detection at debug level too.
- The tray/menu-bar process, `control.port` and autostart (HKCU Run on Windows, LaunchAgent on macOS) live in `beach-viewer` (`background.rs`, `control.rs`, `autostart.rs`, `server_panel.rs`) and run on both platforms. Don't enable the LaunchAgent on this Mac without being asked.
- macOS 26 aborts the process (SIGTRAP in `dispatch_assert_queue`) when Text Input Sources APIs run off the main queue; that includes enigo's `Key::Unicode`. Keyboard layout lookups go through `beach-server/src/keymap.rs`, which hops to the main queue, so the process's main thread must service it (NSApp/winit run loop, or `dispatch_main()` in the CLI).
- macOS Screen Sharing (banner `RFB 003.889`) ignores ClientCutText/ServerCutText from third-party viewers and reads Alt_L as Cmd and Meta_L as Option; `crates/rfb/examples/probe.rs` measures such things.
- Logo/icons: `tools/make-logo.py --raster` (macOS only; renders SVGs through `tools/render-svg.swift`, because `qlmanage` flattens transparency onto white), then `swift tools/make-ios-icon.swift` for the iOS icon. The macOS menu bar icon is `assets/tray.svg` → `assets/tray-template.png` (36×44 px): a monochrome template image, 18 pt artwork in the 22 pt menu bar working area; tray-icon caps the height at 22 pt, so a 44 px tall bitmap maps 1:1 to Retina pixels. Landing page in `docs/` (GitHub Pages).
- macOS app bundle: `tools/build-macos-app.sh` builds a universal `target/macos/VNC Beach.app` (+ zip), signed with the first non-revoked Developer ID/Apple Development identity (the keychain also holds a revoked "Apple Development" cert, SHA-1 9B3A07BA…; apps signed with it hang in `_dyld_start`, and macOS keeps refusing that path afterwards). The x86_64 half needs the keg-only Homebrew rustup (`/opt/homebrew/opt/rustup/bin/rustup target add x86_64-apple-darwin`) and its proxies first in PATH.
- Self-install (Windows, `beach-viewer/src/install.rs`): an exe started anywhere but `%LOCALAPPDATA%\Programs\vnc-beach\vnc-beach.exe` (and outside a `target` dir) copies itself there, writes `%APPDATA%\...\Start Menu\Programs\VNC Beach.lnk`, restarts with `--installed-from <download>` and the installed copy deletes an identical download. Test it with `LOCALAPPDATA`/`APPDATA` pointed at a temp dir and a `config.toml` with `autostart`, `enabled` and `service` off, so the real tray, Run key and service stay alone. The PC build needs `OPENSSL_NO_VENDOR=1 OPENSSL_STATIC=1 OPENSSL_DIR=%LOCALAPPDATA%\vnc-beach\build-deps\openssl-3.6.3` (the vendored build fails: Git's Perl lacks modules).
- Windows release exe: `tools/build-windows.sh` builds on the PC and copies it to `target/windows/VNC-Beach-Windows.exe`; `build.rs` generates the version resource from the crate version.
- Releases: `./release.sh X.Y.Z [--dry-run] [--skip-macos|--skip-windows|--skip-ios]` at the repo root (version bump, tests, both builds, tag, `gh release`, then `tools/release-ios.sh` archives and uploads to TestFlight with the API key from `~/.config/vnc-beach/appstoreconnect.env`; Xcode Cloud is not used for releases). Use `--dry-run` to test; never run a real release unasked.
- Self-update: `beach-viewer/src/update.rs` (system `curl`, GitHub `releases/latest`, assets `VNC-Beach-macOS.zip` / `VNC-Beach-Windows.exe`). Test end to end by serving a GitHub-style JSON and setting `VNC_BEACH_UPDATE_URL`; isolate the config with `HOME=` (macOS) or `APPDATA=` (Windows) so the updater doesn't stop the real background process.
- Accounts (`docs/coordination-server.md`): `crates/beach-coord` is the self-hostable coordination server (axum + SQLite, GitHub/Google OAuth, web UI in `web.rs`, JSON API in `api.rs`); `crates/beach-account` holds the shared API types and Ed25519 tickets. The RFB security type 66 (`rfb::handshake::SECURITY_BEACH_TICKET`) is offered next to VNC auth only by registered servers (`[server.device]` in `config.toml`); the background process sends the heartbeat. The viewer side is `beach-viewer/src/account.rs` (HTTP via system curl, loopback login) and `account_ui.rs`. Test locally with `beach-coord --dev-login --public-url http://127.0.0.1:18080 --listen 127.0.0.1:18080 --data /tmp/x`; never enable `--dev-login` on a public instance. The iOS app doesn't support accounts yet.
- Sebastian's second Mac ("Mac mini von Samuel") is reachable over SSH as `mac-mini-samuel` (host, user and key only in `~/.ssh/config`, not in this public repo) and runs macOS Screen Sharing on port 5900. Copy the app there with scp/ssh (no quarantine attribute) rather than a browser download.
- Testing the server on this Mac: use `cargo run --release -p rfb --example snapshot -- HOST:PORT PASSWORD out.ppm` instead of opening the viewer on the same machine; viewer and server fight over the mouse pointer.
- macOS needs Screen Recording and Accessibility permissions for whatever process launches the server. Without Screen Recording, captures silently contain only wallpaper and menu bar.
- iPad/iPhone app: `apps/ios` (SwiftUI, XcodeGen `project.yml`, committed `VNCBeach.xcodeproj`) links `crates/beach-mobile` (C API over `rfb`, header in `include/`). `tools/build-ios.sh TARGET` builds the static library and runs as an Xcode build phase; it needs a rustup toolchain with `aarch64-apple-ios`/`aarch64-apple-ios-sim` (`brew install rustup`, keg-only at `/opt/homebrew/opt/rustup/bin`) and forces fat LTO because Apple's linker can't read thin-LTO bitcode. Metal shaders compile at runtime (no Metal toolchain installed). Build/test: `cd apps/ios && xcodegen generate && xcodebuild -project VNCBeach.xcodeproj -scheme VNCBeach -destination 'platform=iOS Simulator,name=LifeOS Kitchen iPad' test`; in the simulator `xcrun simctl launch booted at.schlossers.vncbeach -connect "vncbeach://HOST?password=PW"` connects directly. Keep `beach-mobile/src/client.rs` in step with `beach-viewer/src/client.rs`. TestFlight uploads go through `tools/release-ios.sh` (called by `release.sh`; App Store Connect API key in `~/.config/vnc-beach/appstoreconnect.env`), see `apps/ios/README.md`; installing on the iPad with `devicectl` needs the device unlocked.
